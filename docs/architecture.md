# Architecture

**Status:** Evolving; only constraints backed by accepted decisions are stated here.

## Accepted constraints

- The product and user-facing namespace are **Hearth**. `hearthd` names only the core daemon executable; the planned management CLI is `hearth`; companion processes use `hearth-` names; and wire, Entity-type, schema, and Go module identifiers use the `hearth` namespace.
- One trusted Hearth deployment owns one household; version 1 has no separate Site or Home object.
- Home Assistant must ultimately be removable from operation, but specialist protocol services may remain.
- Home Assistant connectivity runs in a disposable migration adapter process separate from the core, communicates across a NATS contract, and is deleted after this household completes migration.
- Core models and wire contracts contain no Home Assistant identifiers, service-call vocabulary, payloads, or lifecycle assumptions.
- The core, simulator, and first-party adapters use module path `github.com/mholtzscher/hearth`. The fixed implementation stack is Go, official `nats.go`, Echo v5, Huma v2, `modernc.org/sqlite`, Goose, sqlc, `coder/websocket`, `jsonschema/v6`, YAML v3, Google UUID, and OpenTelemetry propagation; wire contracts remain language-neutral.
- A thin Go adapter SDK exposes generic Session methods for runtime-scoped registration, durable Observation publication, acknowledged Entity availability reporting, Entity enablement, and ephemeral Command serving. It owns session claim, transient Registration retry, request/reply heartbeat, runtime fencing, and graceful release; Core-only recovery leaves persisted availability visible without an SDK resend, while Adapter code reports configured-external-system condition and fresh Entity availability after actual recovery. Schema-backed typed routing and the built-in power/v1 and brightness/v1 facades let Go adapters register, handle Commands, and encode Observations without raw JSON or operation-name switches. `PublishObservation` retries one generated envelope through transient disconnects and returns only after JetStream acknowledges persistence or the call context expires. Command handler invocations may overlap, including for one Entity; adapters must be concurrency-safe and may serialize internally only when their vendor protocol requires it. The SDK has no local outbox or availability cache and owns no durable state.
- The SDK propagates explicit message, correlation, causation, and command IDs in JSON and W3C trace context in NATS headers.
- One cohesive `devices` product module owns Adapter runtime and health, identity, reconciliation, Entity availability, state projection, and command behavior; those concerns split only after distinct rules and change pressure justify new seams. The Service consumes capability-based persistence stores, while one SQLite repository implements them through the feature-owned `internal/modules/devices/dbsqlc` package. Its `internal/modules/devices/nats` transport owns core-side device NATS payload DTOs, wire/domain mapping, Adapter session and health request/reply, Registration and Entity availability serving, Observation consumption and JetStream policy, and Command sending. Shared Hearth v1 envelope, schema codec, subject, route, and W3C trace mechanics live in `internal/contracts/v1/natswire`; it defines no device payload DTOs. Application assembly retains NATS connection creation, validator compilation, readiness, and process lifecycle.
- Device NATS transport lifecycle names describe the messaging interaction: a `Server` handles Core NATS request/reply and publishes correlated responses, while a `Consumer` reads from a durable JetStream consumer and owns acknowledgement and redelivery behavior. Registration therefore uses `RegistrationServer`; Observation uses `ObservationConsumer`.
- Devices group independently addressable entities; state reads and commands target entities.
- Hearth assigns immutable canonical IDs to devices and entities; adapter-specific external IDs are mappings and ownership can change without changing canonical identity. Canonical and message IDs are UUIDv7 values with type prefixes such as `dev_`, `ent_`, `obs_`, and `cmd_`.
- The first light is bound through explicit configuration and an idempotent registration handshake using Device and Entity names plus minimal capability descriptors: Device kind `light`; Entity type `hearth.power/v1`; support `{"state":{},"operations":{"set":{}}}`. Operation-key presence means support. A registration contains 1-64 independently keyed Entities for one Device and Binding; reconciliation is additive, omitted Entities remain unchanged, and accepted responses contain only submitted mappings in request order. Names and normalized support are persisted Entity metadata and may change without changing canonical identity, while Entity type is immutable. External Entity IDs cannot transfer between keys within one registration. The core returns canonical IDs only after transactionally committing the binding, Device, all submitted Entities, normalized `support_json`, and external mappings. Permanent descriptor, immutable-type, and identity-conflict failures return schema-defined rejected responses that adapters do not retry. Language-neutral JSON Schemas are authoritative for support, State, and parameters; a versioned language-neutral Entity-type manifest associates those schemas with operation names and defines deadlines, outcome matching, and cross-document validation through a small schema-checked relation DSL. Language-neutral examples generate conformance tests. One build-time pass derives all per-type Go, typed SDK facades, and aggregate core catalog assembly; concrete Entity types contain no handwritten Go. Generic JSON crosses transport/persistence seams while typed definitions are erased behind the concrete core catalog. Command resolution uses current support, but immutable outcome callbacks, normalized persisted parameters, and absolute deadlines preserve active Command meaning across re-registration. The built-in catalog contains boolean power and integer brightness definitions; the first-light adapter still uses only power. Runtime type registration, extension loading, runtime manifest loading, general discovery, feature negotiation, configuration schemas, and checkpoints are deferred.
- Each Adapter instance has a configured subject-safe slug and permits one active runtime. A Core session claim returns a fencing-only runtime ID plus a five-second heartbeat interval and fifteen-second lease; graceful release or supervisor-owned lease expiry permits takeover, while a new process cannot evict an active runtime. The supervisor is the only lease-expiry authority, so an active runtime may renew an elapsed lease before the supervisor commits expiry. The runtime ID scopes every post-claim Adapter-originated subject and every Command subject without being repeated in payloads. Core transactionally rejects stale Adapter-originated writes, and the SDK subscribes only to its runtime's Command subject. The runtime ID is neither Adapter identity nor an authentication credential, and the SDK terminates a fenced session. Each configured external object has a stable adapter-scoped binding key so registration preserves canonical IDs when external identifiers change; ambiguous binding/external-ID conflicts reject registration until explicitly reconciled.
- Milestones must provide household value and meaningful NATS learning.
- A production use of NATS must solve a concrete durability, isolation, routing, or observability problem.
- Version 1 wire contracts use a compact Hearth envelope and versioned JSON checked against language-neutral JSON Schemas. Its exact top-level fields are `id`, `schema`, `emitted_at`, required `correlation_id`, optional `causation_id`, and `data`. Canonical schema JSON and a tiny `embed.FS` wrapper live together in importable `contracts/v1`; the core and SDK validate the same embedded schemas at runtime. Incompatible major versions appear in both the subject prefix and each stored payload's schema identifier.
- Wire timestamps are UTC RFC3339Nano strings; malformed or non-UTC values are rejected at the contract edge.
- The SDK generates adapter publication IDs and envelope metadata while adapters supply domain data and diagnostic source times.
- Adapter observations are retained in a file-backed JetStream Limits stream for seven days or one GiB, whichever is reached first, discarding oldest messages. The core uses one explicit-ack durable consumer with a 30-second acknowledgement wait, one maximum pending acknowledgement, and unlimited redelivery. Processed observation IDs remain in SQLite for at least eight days so any retained redelivery stays idempotent; the receipt backing current State remains until a newer Observation supersedes it.
- Each Observation records core-owned `observed_at` from its JetStream server timestamp, adapter-supplied `adapter_received_at`, optional upstream `source_updated_at`, and an internal SQLite `receive_order`. Canonical State follows the tie-free logical `receive_order`; timestamps are operator/history metadata. An `adapter_received_at` more than one minute ahead of `observed_at` is accepted and logged as clock skew.
- Each first-seen, valid, correctly owned Observation advances canonical State. An incoming value must satisfy current support; equality schema-decodes the persisted value without reinterpreting it under support that may have narrowed since persistence. An Observation whose value the Entity-type catalog considers equivalent advances its ID/timestamps and is `unchanged`; a value the catalog considers different is `applied`.
- Core owns reversible Entity enablement. New Entities default to enabled and registration may choose their initial value, while re-registration preserves the current value. Management and the owning Adapter may set enablement idempotently, with SQLite commit order deciding concurrent writes. Disabled Entities retain identity, Binding, metadata, history, and last State and remain visible in reads. Core durably rejects new valid Commands as `entity_disabled` without dispatch and rejects otherwise valid Observations with the same code; only an Observation linked to a matching active pre-disable Command may still project State and satisfy that Command. Core publishes no enablement-change notification, and adapters do not gate Observation publication locally.
- The core owns canonical state, external-ID mappings, Observation receipts, Command history, Adapter runtime and health, Entity availability reports, exact health and availability transitions, and Entity enablement transactionally in SQLite; NATS KV is not used for these models. Health and availability transitions are retained indefinitely. Adapter transitions and explicit Entity reports are stored once; effective Entity history includes owning-Adapter transitions from the Entity's initial transition onward rather than using fan-out writes.
- SQLite migrations use Goose and query code is generated in one feature-owned `devices` package from concern-specific query files; generated persistence types do not cross the module seam.
- Every observation has an immutable ID that the core records transactionally with its disposition and state projection, making exact JetStream redelivery a no-op.
- Permanently invalid Observations are diagnosed in structured logs with safe payload metadata and acknowledged; raw input remains in the seven-day stream. Transient infrastructure failures remain unacknowledged for redelivery. Valid applied, unchanged, duplicate, and rejected Observations are acknowledged only after the SQLite transaction commits.
- Immediate commands use adapter-scoped Core NATS request/reply, take their end-to-end deadline from the registered operation definition, and are not queued for later adapter recovery. The first `hearth.power/v1` `set` operation has a fixed ten-second deadline.
- Commands for one Entity may overlap; the core does not guard, queue, or supersede them. Each Command has an independent ID, durable record, in-memory waiter, and operation-defined deadline, and only its own linked Observation satisfying the catalog outcome policy can complete it. Interleaved Commands may both be satisfied at different receive orders or may cause one another to time out; canonical State still follows core receive order.
- Command delivery and outcome waits are ephemeral and in memory, while SQLite stores a minimal non-replayable record of each attempt and terminal outcome for diagnosis and future history. The record commits as `requested` before dispatch; a linked Observation satisfying the catalog outcome policy marks only that Command `satisfied` in the same transaction as State projection. After the `requested` record commits, the core proceeds with dispatch and retains that lifecycle until linked outcome or the operation-defined deadline even if the HTTP client disconnects. Only the startup-wide interruption path may mark persisted `requested` and `accepted` records `interrupted`; per-command completion cannot claim a core restart. A core restart loses active waits and never redispatches them.
- `GET /v1/entities/{entity_id}` returns Entity metadata and current State; a registered but never-observed Entity returns `state: null` rather than 404 or synthetic state.
- Resource discovery adds `GET /v1/entities`, `GET /v1/devices`, and `GET /v1/devices/{device_id}`. Entities remain top-level canonical resources, Entity listing may filter by `device_id`, and Device detail embeds a page of associated Entities with nullable current State and nested availability. Adapter management adds stable-slug list and detail reads with current health, runtime lease and configured-external-system evidence, plus paginated Adapter health and effective Entity availability histories. Collection reads use opaque endpoint-scoped keyset cursors, default to 50 items, accept limits from 1 through 200, omit totals, and return no continuation cursor on the last page; Device detail uses `entity_limit`, `entity_cursor`, and `next_entity_cursor` for its embedded collection.
- Durable Command audit reads add `GET /v1/commands/{command_id}` and `GET /v1/entities/{entity_id}/commands`. History is ordered by fixed-width persisted request time and Command ID newest-first, distinguishes an unknown Entity from empty history, and exposes persisted operation parameters and outcomes without adapter or correlation identifiers or synthesized historical values.
- HTTP pagination cursors are unsigned, versioned base64url JSON positions scoped to their endpoint, optional Device filter, parent Device, and parent Entity. They provide position rather than authority and are not security credentials.
- `POST /v1/entities/{entity_id}/commands` accepts `{"operation":"set","parameters":{"value":true}}` for the first power Entity and waits synchronously for outcome satisfaction or deadline failure.
- HTTP errors use Huma's standard RFC 9457 Problem Details model and validation conventions. Command status mappings include unhealthy or unrouted Adapter 503, Entity-unavailable rejection 503, upstream rejection 502, outcome timeout 504, and internal failure 500.
- The unauthenticated HTTP API binds to its configured address. Configuration examples remain loopback-only; non-loopback binding is an explicit operator choice for trusted networks, and untrusted network exposure requires authentication and a deployment decision.
- Each first-slice process owns a separate YAML file for non-secret configuration; the Home Assistant adapter reads its token from a separate local secret file.
- Adapter health is one `unknown`, `healthy`, or `unhealthy` assessment with separately exposed runtime and configured-external-system evidence. Core request/reply heartbeats immediately repeat the Adapter's current assessment, renew only the dedicated runtime lease, and commit status or reason-code transitions; unchanged reports refresh current evidence without creating history. Graceful release makes health immediately `unhealthy`.
- Entity availability is `unknown`, `available`, or `unavailable`; Devices have no health. Only explicit acknowledged reports from the active healthy owning Adapter set Entity availability, reports may still update disabled Entities, and an unhealthy Adapter makes every owned Entity effectively unavailable. A transition away from healthy deletes current Entity reports transactionally, so later recovery requires fresh atomic partial batches of 1-256 owned Entities; unknown is Core-derived and unavailable reports require a reason.
- An unhealthy owning Adapter causes a new Command to fail as `adapter_unhealthy` before dispatch. Unknown Adapter health is attempted only when an active runtime route exists; an unavailable Entity with a healthy owner is also attempted, and a fresh typed rejection may fail as `entity_unavailable` without itself writing availability. Entity disablement still wins when both conditions apply.
- Health and availability use Core receive order and Core-owned time for canonical transitions while retaining Adapter-observed source time for diagnosis. Negative reports require stable reason codes: shared codes use the `hearth.` namespace and Adapter-defined codes use `adapter.` without coupling validation to runtime software metadata. Status or reason-code changes create history transitions; repeated evidence does not.
- At startup and reconnect, the disposable Home Assistant adapter establishes its state-change subscription before requesting a current snapshot, buffers events during snapshot acquisition, and reconciles them by Home Assistant `last_updated` before live publication so no transition is lost or allowed to overwrite a newer snapshot. It correlates concurrent WebSocket requests by request ID and explicitly publishes each accepted Command's own linked refresh.
- A command is dispatched even when canonical state already matches its requested target.
- After upstream acceptance, the adapter actively refreshes state and publishes a fresh observation linked to the command ID, including when no state-change event occurred.
- A command outcome is satisfied only after the linked post-dispatch canonical Observation satisfies the registered operation's catalog outcome policy; for the first `set` operation this means its value matches the requested value. This claims that the outcome was observed, not that the Command caused it.
- Version 1 Adapter routes atomically cut over from stable-slug-only subjects to a stable-slug session claim plus Core-issued runtime-scoped Registration, heartbeat, release, Observation, Command, Entity enablement, and Entity availability subjects. Runtime IDs are not repeated in payloads. Entity availability uses acknowledged Core NATS request/reply with Adapter retry for transient failures; a batch rejects atomically on any invalid or wrongly owned entry. Core, embedded contracts, first-party Adapters, the Go SDK, and NATS resources ship this incompatible cutover together, and mixed versions remain unsupported.
- Echo v5 and Huma v2 provide HTTP transport; application assembly constructs them and owns process-global HTTP framework policy, while the `devices` module owns operation registration and transport mapping. OpenAPI is exposed at runtime and is not committed as a generated artifact.
- Local development runs Go binaries and NATS natively through mise; container packaging is deferred until deployment work.
- The core exposes `/healthz` and `/readyz` on its configured HTTP address; readiness requires migrated SQLite, NATS connectivity, provisioned JetStream resources, and an active observation consumer. Core readiness supersedes Adapter health for diagnosis: readiness failure pauses the supervisor's lease expiry without changing persisted Adapter or Entity reads, and recovery grants one lease interval of expiry grace before polling resumes. Other Adapter operations verify active runtime identity but do not expire leases. Persisted child assessments remain visible but non-authoritative while `/readyz` fails. Adapters retry transient claim and registration failures until the core is available and stop on schema-defined permanent rejection.

## Undecided
