# Architecture

**Status:** Evolving; only constraints backed by accepted decisions are stated here.

## Accepted constraints

- The product and user-facing namespace are **Hearth**. `hearthd` names only the core daemon executable; the planned management CLI is `hearth`; companion processes use `hearth-` names; and wire, Entity-type, schema, and Go module identifiers use the `hearth` namespace.
- One trusted Hearth deployment owns one household; version 1 has no separate Site or Home object.
- Home Assistant must ultimately be removable from operation, but specialist protocol services may remain.
- Home Assistant connectivity runs in a disposable migration adapter process separate from the core, communicates across a NATS contract, and is deleted after this household completes migration.
- Zigbee2MQTT connectivity runs in a stateless first-party companion process while Zigbee2MQTT, the coordinator, and broker remain operator-managed specialist services. The process uses a native Hearth SDK Session for Core communication and a private Paho MQTT 3.1.1 client for Zigbee2MQTT traffic; the MQTT broker is a separate specialist service and is not a NATS listener, so translated Zigbee2MQTT traffic never bypasses MQTT. MQTT sessions are clean and reconnect behavior belongs to the Adapter.
- The Zigbee2MQTT Adapter plans Entities from complete retained inventory through explicit light, relay, sensor, link-quality, and action planners sharing one expose index. Normalized IEEE address and numeric endpoint identity determine one canonical Device's stable Binding and Entity keys; friendly names are mutable route metadata. A non-empty light result is the primary family, otherwise a non-empty relay result wins; temperature, humidity, illuminance, battery, occupancy, link-quality, and action plans are supplemental, so they append to either actuator family and form a sensor-only Device only when no light or relay plan exists. One IEEE address yields one registration with Device kind `light`, `relay`, or `sensor`. Light power gates its family with optional brightness, mode-aware color-temperature, native XY color, native HS color, and read-only color-mode siblings; relay roots produce power through the same power constructor, and surviving relay power gates the shared power-on behavior setting, six read-only electrical sensors (AC frequency, electrical power under the `electricalpower` key, power factor with an empty upstream unit mapped to `ratio`, energy, current, voltage), three observable numeric settings (LED brightness and both turn on/off countdowns), and the stateless reset-total-energy action; the sensor planner produces read-only temperature, humidity, illuminance, battery, and occupancy Entities, with occupancy the first record of the sensor family's binary capability table. Binary capability records claim every resolved root binary expose whose name matches a record and that carries publish access, no set access, a non-empty Device-unique State property and endpoint supplied by inventory, and present distinct `value_on`/`value_off` scalars; distinct endpoint-scoped roots keep distinct `-ep<N>` keys while same-key duplicates are omitted. Illuminance claims root numeric exposes named `illuminance` with exact unit `lx`, publish access, no set access, and a non-empty Device-unique State property supplied by inventory; an ambiguous or malformed candidate omits only that Entity. Root and unambiguously resolved endpoint exposes produce Entity keys `power`, `poweronbehavior`, `brightness`, `colortemp`, `colorxy`, `colorhs`, `colormode`, `acfrequency`, `electricalpower`, `powerfactor`, `energy`, `current`, `voltage`, `ledbrightness`, `countdowntoturnoff`, `countdowntoturnon`, `resettotalenergy`, `effect`, `temperature`, `humidity`, `illuminance`, `battery`, `occupancy`, and `linkquality` plus `-ep<N>` forms, while invalid Devices, exposes, or optional features are isolated. Electrical sensors use conservative validation envelopes, not claimed operating ranges, because Zigbee2MQTT omits their bounds; both valid finite upstream electrical bounds are preferred when present, while malformed, one-sided, or inverted bounds omit only that Entity. Ambient illuminance independently uses a fixed 0–1000000000 lx validation envelope. Startup and recovery reconcile complete SDK-owned mapping inventory so missing, disabled, and capability-removed resources remain canonically identified and become unavailable rather than being deleted.
- Zigbee2MQTT health requires an online bridge, MQTT 3.1.1, explicit availability enabled, global optimistic behavior proven false, and a completed inventory reconciliation. Entity availability comes only from explicit per-Device evidence, while retained or live Device State may produce typed power, normalized integer brightness, object color-temperature with mode activity, native XY and HS color States with mode activity, read-only color-mode, integer milli-Celsius ambient-temperature Observations, 0–100 percent humidity and battery Observations, lux illuminance Observations under a fixed 0–1000000000 validation envelope, boolean occupancy Observations decoded from the expose's declared on/off scalars, smart-plug electrical Observations (Hz, W, ratio, kWh, A, V with fractions preserved), value-mode numeric-setting States for LED brightness and both countdowns, and enum-setting power-on behavior States. Color coordinate and temperature activity derives from the same-message reported color mode, never from cached assembly; a temperature-only root with no reported mode stays active. Temperature, humidity, illuminance, battery, occupancy, and electrical plans carry a nil command translator, never enter command routes, and expose get properties only when the upstream expose grants get access; startup `/get` covers only Entities with non-empty get properties. A private generic runtime coordinator owns routes, MQTT generations, per-IEEE FIFO Command queues, matchers, deadlines, and State disposition. It serializes Commands across all controllable Entity kinds per IEEE Device, runs blocking MQTT and Observation work outside its event loop, accepts after QoS 1 `/set` PUBACK, triggers `/get` for every accepted observed Command, and uses a fresh non-retained matching report under mode-aware outcome policies (exact active mireds; bounded XY/HS tolerances) as command-linked outcome evidence. Dispatched effect and reset-total-energy attempts publish no `/get`, install no matcher, and publish no observation. Multi-property plans require complete same-message evidence and the Adapter keeps no cross-message State cache. Entity plans remain property-local by default; multi-property plans are appropriate only when the upstream value is genuinely atomic and complete in one MQTT message. Zigbee2MQTT cache-expanded payload completeness does not prove sibling properties were freshly observed together, and the Adapter must not require or depend on `cache_state=true` to assemble Entity State.
- The Zigbee2MQTT v1 MQTT boundary is unauthenticated plain TCP and accepts only explicit host-and-port URLs. The native NATS listener and the Mosquitto MQTT broker must bind to loopback or a trusted private network; MQTT authentication, TLS, and untrusted-network exposure are unsupported. Base topics are subject-safe slugs and friendly names are single MQTT topic levels, so topic classification remains unambiguous.
- Ecowitt connectivity runs in a stateless first-party companion process while the GW2000 gateway, its Customized Server MQTT publishing, a WS90 outdoor array, and the Mosquitto broker remain operator-managed. The process uses a native Hearth SDK Session for Core communication and a private Paho MQTT 3.1.1 client for one exact station topic; the MQTT listener must bind to loopback or a trusted private network, v1 uses plain unauthenticated MQTT with no username, password, TLS, WebSocket, or durable session, and Adapter-owned reconnect uses a clean session and the deterministic 23-character client ID `hearth-eco-` plus the first twelve lowercase hexadecimal characters of SHA-256(adapter_id). The configured 32-character hexadecimal PASSKEY is loaded from a separate secret file, compared in constant time, and never logged, exported, hashed into metadata, or persisted. One Adapter instance serves one GW2000-prefixed station and registers exactly two slot Devices of kind `sensor`: `gateway` with indoor temperature, indoor humidity, relative pressure, and absolute pressure, and `outdoor-array` with WS90 outdoor temperature, outdoor humidity, wind direction, wind speed, wind gust, maximum daily gust, solar radiation, UV index, and seven piezo-rain Entities (rate, event, hourly, daily, weekly, monthly, yearly). Binding keys (`gateway`, `outdoor-array`), Device external IDs, and Entity external IDs (`<device external ID>/<entity key>`) carry no PASSKEY, topic, station MAC, firmware, or display name, so replacing hardware in a configured slot preserves canonical IDs while a separately meaningful station requires a different `adapter_id`. Reports are the URL-encoded Customized Server form body, not JSON; the Adapter accepts only a non-retained, non-duplicate, structurally valid, compatible report of at most 64 KiB and 256 unique fields on the exact topic, requires one matching PASSKEY and a `GW2000` station-type prefix, uses one `dateutc` as an optional sane source time, and converts Fahrenheit, inches of mercury, miles per hour, and inches to integer milli-Celsius and decimal hPa, m/s, and mm (or mm/h) with fixed constants. Each Entity is independent: an absent, malformed, non-finite, or out-of-envelope measurement produces no Observation and never suppresses a valid sibling, and out-of-envelope values are rejected rather than clamped. Adapter health stays unknown until positive or negative evidence; MQTT connect, disconnect, subscription, and relay-overflow failures use `hearth.external_system_unavailable`, and three configured upload intervals without a fresh accepted report use `adapter.hearth-adapter-ecowitt.station_silent`. Every unhealthy transition clears Entity availability, so recovery requires a fresh live report, an acknowledged healthy transition, and explicit availability before Observations; a valid field becomes explicitly available, and an Entity without one for three intervals becomes unavailable with `adapter.hearth-adapter-ecowitt.measurement_stale`. Every non-duplicate report publishes one typed Observation per present valid measurement in catalog order with a shared Adapter receive time, never suppresses an unchanged value, and keeps no checkpoint, outbox, or cross-restart value cache; a bounded serial coordinator owns MQTT generations, connection-local duplicate suppression, freshness deadlines, and ordered report work, while blocking SDK calls run in tracked effect goroutines so the event loop never blocks on an acknowledgement. Retained, wrong-topic, wrong-PASSKEY, wrong-station-type, malformed, oversized, over-field-limit, duplicate-key, and exact-duplicate reports produce no evidence and refresh no freshness deadline; diagnostics log fixed codes and payload lengths only and never repeat the configured topic, PASSKEY, secret-file contents, raw payload, or field values.
- Core models and wire contracts contain no Home Assistant or Zigbee2MQTT identifiers, service-call vocabulary, payloads, or lifecycle assumptions.
- The core, simulator, and first-party adapters use module path `github.com/mholtzscher/hearth`. The fixed implementation stack is Go, official `nats.go`, Echo v5, Huma v2, `modernc.org/sqlite`, Goose, sqlc, `coder/websocket`, `jsonschema/v6`, YAML v3, Google UUID, and OpenTelemetry propagation; wire contracts remain language-neutral.
- A thin Go adapter SDK exposes generic Session methods for runtime-scoped registration, one-page Adapter-owned mapping inventory, durable ordinary Observation publication, acknowledged Entity availability reporting, Entity enablement, and ephemeral Command serving. A successful one-shot `Responder.Accept` returns a command-evidence capability that alone can publish Observations linked to that accepted Command; its caller context may shorten publication but cannot extend the Command deadline, and handler return does not cancel it. The public Observation types contain no raw Command link. The private publication path preserves the existing wire `refresh_for_command_id`, matching causation, correlation, trace metadata, stable retry identity, JetStream acknowledgement, fencing, and error classification. The SDK owns session claim, transient Registration retry, request/reply heartbeat, runtime fencing, and graceful release; Core-only recovery leaves persisted availability visible without an SDK resend, while Adapter code reports configured-external-system condition and fresh Entity availability after actual recovery. Schema-backed typed routing and the built-in power/v1, brightness/v1, colortemp/v1, colorxy/v1, colorhs/v1, colormode/v1, temperature/v1, relativehumidity/v1, pressure/v1, speed/v1, numericsensor/v1, binarysensor/v1, enumsetting/v1, numericsetting/v1, enumaction/v1, and enumevent/v1 facades let Go adapters register, handle Commands, encode ordinary Observations, and validate and report Entity Events without raw JSON or operation-name switches. Command handler invocations may overlap, including for one Entity; adapters must be concurrency-safe and may serialize internally only when their vendor protocol requires it. The SDK has no local outbox, availability cache, or mapping cache and owns no durable state.
- The SDK propagates explicit message, correlation, causation, and command IDs in JSON and W3C trace context in NATS headers.
- One cohesive `devices` product module owns Adapter runtime and health, identity, reconciliation, Entity availability, state projection, and command behavior; those concerns split only after distinct rules and change pressure justify new seams. The Service consumes capability-based persistence stores, while `internal/modules/devices/sqlite` implements them with one SQLite repository and owns its `dbqueries` sources and generated `dbsqlc` package. SQLite imports the devices domain, never the reverse; application assembly selects the repository and injects its stores. Domain policies stay independent of SQL row types, while transaction-dependent decisions run against data loaded inside the repository's existing atomic operations. Its `internal/modules/devices/nats` transport owns core-side device NATS payload DTOs, wire/domain mapping, Adapter session and health request/reply, Registration and Entity availability serving, Observation consumption and JetStream policy, Command sending, and the Device Fact outbox, stream and single durable relay. Shared Hearth v1 envelope, schema codec, subject, route, and W3C trace mechanics live in `internal/contracts/v1/natswire`; it defines no device payload DTOs. Application assembly retains NATS connection creation, validator compilation, readiness, and process lifecycle.
- Device NATS transport lifecycle names describe the messaging interaction: a `Server` handles Core NATS request/reply and publishes correlated responses, while a `Consumer` reads from a durable JetStream consumer and owns acknowledgement and redelivery behavior. Registration therefore uses `RegistrationServer`; Observation, Entity Event, and Device Fact constructors return the shared `platformnats.Consumer` lifecycle while their modules retain message handling and acknowledgement policy. Device Fact types state their role explicitly: `devices.DeviceFactOutbox` is the durable pending set the relay drains, `devices.DeviceFactNotifier` is the nonblocking wake hint devices uses after a commit, and `devicesnats.DeviceFactRelay` owns the single oldest-first publisher over the shared connection.
- `platform/lifecycle.WorkerHandle` owns cancellation and joining for the Core health supervisor, Device Fact relay, and history pruning worker. It does not own scheduling, retries, readiness, or fault policy. Unlike admission draining, stopping a worker requests cancellation; a wait timeout never proves that the worker has exited.
- Devices group independently addressable entities; state reads and commands target entities.
- Hearth assigns immutable canonical IDs to devices and entities; adapter-specific external IDs are mappings and ownership can change without changing canonical identity. Canonical and message IDs are UUIDv7 values with type prefixes such as `dev_`, `ent_`, `obs_`, and `cmd_`.
- The first light is bound through explicit configuration and an idempotent registration handshake using Device and Entity names plus minimal capability descriptors: Device kind `light`; Entity type `hearth.power/v1`; support `{"state":{},"operations":{"set":{}}}`. Operation-key presence means support. A registration contains 1-64 independently keyed Entities for one Device and Binding; reconciliation is additive, omitted Entities remain unchanged, and accepted responses contain only submitted mappings in request order. Names and normalized support are persisted Entity metadata and may change without changing canonical identity, while Entity type is immutable. External Entity IDs cannot transfer between keys within one registration. The core returns canonical IDs only after transactionally committing the binding, Device, all submitted Entities, normalized `support_json`, and external mappings. Permanent descriptor, immutable-type, and identity-conflict failures return schema-defined rejected responses that adapters do not retry. Language-neutral JSON Schemas are authoritative for support, State, and parameters; a versioned language-neutral Entity-type manifest associates those schemas with operation names and defines deadlines, outcome matching, and cross-document validation through a small schema-checked relation DSL. Language-neutral examples generate conformance tests. One build-time pass derives all per-type Go, typed SDK facades, and aggregate core catalog assembly; concrete Entity types contain no handwritten Go. Generic JSON crosses transport/persistence seams while typed definitions are erased behind the concrete core catalog. Command resolution uses current support, but immutable outcome callbacks, normalized persisted parameters, and absolute deadlines preserve active Command meaning across re-registration. The built-in catalog contains boolean power, integer brightness, object color-temperature with mode activity, scaled-integer XY color, integer HS color, color-mode enum, integer milli-Celsius temperature, reusable read-only relative-humidity, pressure, and speed quantities with fixed percent, hPa, and m/s State declared in structured State support and empty operations, read-only boolean binary sensor, generic read-only number sensor, generic observable enum and numeric settings, generic stateless enum action definitions with empty temperature, mode, sensor, and binary operation support, and a generic stateless, non-commandable event source (`hearth.enumevent/v1`) whose support lists 1–64 supported Entity Event name slugs. Runtime type registration, extension loading, runtime manifest loading, general discovery, feature negotiation, configuration schemas, and checkpoints are deferred.
- Each Adapter instance has a configured subject-safe slug and permits one active runtime. The SDK generates one fencing-only runtime ID and retries the same claim request and runtime ID until Core acknowledges it; Core persists the supplied runtime ID idempotently without a separate claim-to-runtime mapping. Graceful release or supervisor-owned lease expiry permits takeover, while a new process cannot evict an active runtime. Heartbeats use a fixed five-second interval and renew a fifteen-second lease. The supervisor is the only lease-expiry authority, so an active runtime may renew an elapsed lease before the supervisor commits expiry. The runtime ID scopes every post-claim Adapter-originated subject and every Command subject without being repeated in later payloads. Core transactionally rejects stale Adapter-originated writes, and the SDK subscribes only to its runtime's Command subject. The runtime ID is neither Adapter identity nor an authentication credential, and the SDK terminates a fenced session. Each configured external object has a stable adapter-scoped binding key so registration preserves canonical IDs when external identifiers change; ambiguous binding/external-ID conflicts reject registration until explicitly reconciled.
- An active Adapter runtime may read Core's persisted `(binding_key, device_id, entity_key, entity_id)` mappings only for its subject-scoped Adapter identity. The runtime-fenced NATS request returns flat rows ordered by Binding and Entity key, one explicit page at a time; it exposes no descriptors, external IDs, State, availability, or enablement. The transport owns an unsigned, unpadded base64url JSON cursor scoped by version, resource, and Adapter; trailing JSON, invalid or noncanonical encoding, malformed keys, and scope mismatches are invalid. Cursor positions are lexical and need not identify an existing row. Keyset pages are not snapshots: concurrent registrations after a cursor may appear, while inserts before it may not. Runtime validity follows the existing supervisor-owned runtime state rather than independently comparing the lease timestamp during this read.
- Milestones must provide household value and meaningful NATS learning.
- A production use of NATS must solve a concrete durability, isolation, routing, or observability problem.
- Version 1 wire contracts use a compact Hearth envelope and versioned JSON checked against language-neutral JSON Schemas. Its exact top-level fields are `id`, `schema`, `emitted_at`, required `correlation_id`, optional `causation_id`, and `data`. Canonical schema JSON and a tiny `embed.FS` wrapper live together in importable `contracts/v1`; the core and SDK validate the same embedded schemas at runtime. Incompatible major versions appear in both the subject prefix and each stored payload's schema identifier.
- Wire timestamps are UTC RFC3339Nano strings; malformed or non-UTC values are rejected at the contract edge.
- The SDK generates adapter publication IDs and envelope metadata while adapters supply domain data and diagnostic source times.
- Adapter observations are retained in a file-backed JetStream Limits stream for seven days or one GiB, whichever is reached first, discarding oldest messages. The core uses one explicit-ack durable consumer with a 30-second acknowledgement wait, one maximum pending acknowledgement, and unlimited redelivery. Processed observation IDs remain in SQLite for at least eight days so any retained redelivery stays idempotent; the observation backing current State remains until a newer Observation supersedes it.
- Each Observation records core-owned `observed_at` from its JetStream server timestamp, adapter-supplied `adapter_received_at`, optional upstream `source_updated_at`, and an internal SQLite `receive_order`. Canonical State follows the tie-free logical `receive_order`; timestamps are operator/history metadata. An `adapter_received_at` more than one minute ahead of `observed_at` is accepted and logged as clock skew.
- Each first-seen, valid, correctly owned Observation advances canonical State. An incoming value must satisfy current support; equality schema-decodes the persisted value without reinterpreting it under support that may have narrowed since persistence. An Observation whose value the Entity-type catalog considers equivalent advances its ID/timestamps and is `unchanged`; a value the catalog considers different is `applied`.
- Core owns reversible Entity enablement. New Entities default to enabled and registration may choose their initial value, while re-registration preserves the current value. Management and the owning Adapter may set enablement idempotently, with SQLite commit order deciding concurrent writes. Disabled Entities retain identity, Binding, metadata, history, and last State and remain visible in reads. Core durably rejects new valid Commands as `entity_disabled` without dispatch and rejects otherwise valid Observations with the same code; only an Observation linked to a matching active pre-disable Command may still project State and satisfy that Command. Core publishes no enablement-change notification, and adapters do not gate Observation publication locally.
- The core owns canonical state, external-ID mappings, Observations, Command history, Adapter runtime and health, Entity availability reports, exact health and availability transitions, and Entity enablement transactionally in SQLite; NATS KV is not used for these models. Health and availability transitions are retained indefinitely. Adapter health transitions are stored once and transactionally fan out materialized effective availability transitions to owned Entities when status or reason changes; source-only changes do not create transitions.
- SQLite migrations use Goose and query code is generated in one feature-owned `devices` package from concern-specific query files; generated persistence types do not cross the module seam.
- Every observation has an immutable ID that the core records transactionally with its disposition and state projection, making exact JetStream redelivery a no-op.
- Entity State history enriches that same first-seen Observation rather than adding a parallel history table or insert. Applied and unchanged observations contain normalized canonical State JSON; rejected observations contain a rejection code and no raw value. All dispositions retain the optional source timestamp. Observation Entity IDs deliberately have no foreign key so unknown-Entity and stale-runtime rejections remain durable. One `observation_retention` Core setting (default 30 days, minimum 8 days) bounds history together with observations: each hourly prune deletes non-current observations with `observed_at` older than the window, deriving the cutoff on every pass so policy changes apply to already persisted rows without rewriting them. The observation backing current State remains an older anchor until superseded. Pruning is eligibility, not an exact TTL: a background startup pass applies the configured window after recovery, followed by a pass one hour after each preceding pass finishes. The app owns the shared `HistoryPruner` schedule, cancellation/joining, and safe per-module failure logs; modules own retention policy, cutoffs, and deletion behavior. Passes run devices then automations with one UTC sweep time, never overlap or replay missed ticks, never gate readiness, and are joined before SQLite closes. No historical backfill, archive, aggregate, NATS resource, or additional prune loop is introduced. Since Hearth has no deployments, this schema change modifies migration 00001 directly: existing development databases must be recreated.
- Permanently invalid Observations are diagnosed in structured logs with safe payload metadata and acknowledged; raw input remains in the seven-day stream. Transient infrastructure failures remain unacknowledged for redelivery. Valid applied, unchanged, duplicate, and rejected Observations are acknowledged only after the SQLite transaction commits.
- Immediate commands use adapter-scoped Core NATS request/reply, take their end-to-end deadline from the registered operation definition, and are not queued for later adapter recovery. The first `hearth.power/v1` `set` operation has a fixed ten-second deadline.
- Commands for one Entity may overlap; the core does not guard, queue, or supersede them. Each Command has an independent ID, durable record, in-memory waiter, and operation-defined deadline. An observed operation completes only through its own linked Observation satisfying the catalog outcome policy, while a dispatched operation completes on durable acceptance without observation. Interleaved Commands may both be satisfied at different receive orders or may cause one another to time out; canonical State still follows core receive order.
- Command delivery and outcome waits are ephemeral and in memory, while SQLite stores a minimal non-replayable record of each attempt and terminal outcome for diagnosis and future history. The record commits as `requested` before dispatch; for observed operations a linked Observation satisfying the catalog outcome policy marks only that Command `satisfied` in the same transaction as State projection, while a dispatched operation commits `dispatched` on acceptance with no observation or state. After the `requested` record commits, the core proceeds with dispatch and retains that lifecycle until linked outcome or the operation-defined deadline even if the HTTP client disconnects. Only the startup-wide interruption path may mark persisted `requested` and `accepted` records `interrupted`; per-command completion cannot claim a core restart. A core restart loses active waits and never redispatches them.
- `GET /v1/entities/{entity_id}` returns Entity metadata and current State; a registered but never-observed Entity returns `state: null` rather than 404 or synthetic state.
- Resource discovery adds `GET /v1/entities`, `GET /v1/devices`, and `GET /v1/devices/{device_id}`. Entities remain top-level canonical resources, Entity listing may filter by `device_id`, and Device detail embeds a page of associated Entities with nullable current State and nested availability. Adapter management adds stable-slug list and detail reads with current health, its Core or Adapter evidence source, runtime lease evidence, and paginated Adapter health and effective Entity availability histories. Collection reads use opaque endpoint-scoped keyset cursors, default to 50 items, accept limits from 1 through 200, omit totals, and return no continuation cursor on the last page; Device detail uses `entity_limit`, `entity_cursor`, and `next_entity_cursor` for its embedded collection.
- Durable Command audit reads add `GET /v1/commands/{command_id}`, `GET /v1/commands`, and `GET /v1/entities/{entity_id}/commands`. History is ordered by fixed-width persisted request time and Command ID newest-first, distinguishes an unknown Entity from empty history, and exposes persisted operation parameters and outcomes without adapter or correlation identifiers or synthesized historical values. The household list accepts optional `entity_id` and `status` filters; an unknown but canonical Entity filter matches nothing instead of failing, mirroring the Entity list Device filter.
- `GET /v1/entities/{entity_id}/state/history` reads retained observations newest-first by receive order. The default `state-updates` filter includes applied and unchanged evidence; `all`, `applied`, `unchanged`, and `rejected` are also supported. It verifies the parent Entity first (unknown is 404; existing but empty is an empty array), defaults to 50 items, and accepts limits 1–200. Three static indexed query families provide selective ordered reads for all, updates, and individual dispositions. The response exposes normalized accepted values and diagnostic timestamps, never raw rejected values, Adapter/runtime IDs, expiry, or receive order. Continuation cursors bind the Entity, effective filter, and strict lower receive order. Pages are not snapshots: newer Observations require restarting, pruning can yield an empty continuation, and cursors need not identify an extant observation. The dashboard plots only the current page on an explicitly ordinal, non-time axis; unchanged-only results are isolated points, malformed accepted values break paths, and current support cannot clip historical values.
- Entity Events are named occurrence reports, not State. The built-in stateless, non-commandable `hearth.enumevent/v1` type carries empty State and Operations support plus a bounded list of supported event-name slugs, generates no Observation or Command facade, and always reads `state:null`. Only a currently supported name of a type with a generated name selector is accepted; a stale runtime, unknown Entity, wrong owner, disabled Entity, or unsupported name rejects with a fixed code without changing State, Commands, bindings, enablement, health, or availability. Non-event classification precedes support decoding, so a resolved non-event type rejects with `unsupported_event` even when its persisted support is malformed; corrupt descriptors are catalog failures only when Core interprets an event-source descriptor, and that failure is the permanent `ErrEntityEventDescriptorCorrupt` class the consumer terminates. Acceptance means the report passed processing-time rules, never physical truth or causation.
- Wire `urn:hearth:schema:entity-event:v1` is a strict envelope with `evt_` identity, `cor_` correlation, SDK `emitted_at`, and no `causation_id`, arbitrary payload, or source-time field, carried on `hearth.v1.adapter.<adapter>.runtime.<runtime>.entity-event.<entity_id>`. SDK publication mints the ID and correlation once and reuses one ID, byte encoding, subject, `Nats-Msg-Id`, and trace metadata across transient JetStream retries until PubAck, caller cancellation or deadline, a permanent error, or Session termination, returning the minted ID with later errors so an ambiguous report never gets a new identity. PubAck is storage acknowledgement, not Core acceptance; Core verifies subject/payload Entity agreement and MsgId/envelope identity before persistence.
- Entity Events use an independent file-backed JetStream Limits stream (`HEARTH_ENTITY_EVENTS_V1`, subject filter `hearth.v1.adapter.*.runtime.*.entity-event.*`, seven days or one GiB, 4 KiB maximum message, DiscardOld) with a dedicated durable explicit-ack consumer (`hearthd-entity-events-v1`, DeliverAll, ReplayInstant, 30-second AckWait, unlimited redelivery, one maximum pending acknowledgement), so button and gesture history can never be mistaken for State. One pending slot is safe because every deterministic per-report failure is resolved before it can hold that slot: a report whose persisted event-source descriptor Core cannot interpret is terminated, which releases the slot immediately, while a report only storage failed to record is negatively acknowledged after a bounded delay, so a single uninterpretable or unrecordable report can never permanently stop unrelated history from being delivered. Core provisions both streams and both consumers before transports, rejects incompatible existing configuration, and reports resource compatibility and consumer activity through readiness without waiting for backlog exhaustion or gating ingestion. Age is not a rejection reason; Core may log SDK clock skew without gating recording or ordering.
- One `entity_events` table records each first-seen wire-valid report and its disposition in one devices-owned transaction after supervisor-fenced runtime, Entity existence, ownership, enablement, and current support checks. The fingerprint over the canonical immutable tuple detects a changed-input identity conflict while `event_id` remains the lookup key, `receive_order` provides an order that is independent of State and has no ties, and duplicate or conflicting input preserves the first row, its disposition, and its timestamps. Core records JetStream storage time as `received_at` and its own first-record time as `recorded_at`. Wire-invalid input, a missing or mismatched `Nats-Msg-Id`, unexpected causation, and route mismatch are acknowledged with a safe permanent class and create no row; accepted, rejected, and duplicate results are acknowledged only after the repository establishes them. A record or commit failure is never positively acknowledged and writes no partial row: a failure to interpret the Entity's persisted event-source descriptor is a permanent `ErrEntityEventDescriptorCorrupt` failure that the consumer terminates, leaving the raw report in the bounded stream as its only remaining evidence and writing no history row, while every other record or commit failure is negatively acknowledged after a bounded delay equal to the AckWait so it stays redeliverable without limit. Reprocessing one identity never reclassifies it, and recording changes no State, Commands, bindings, enablement, health, or availability.
- Entity Event history is read through `GET /v1/entities/{entity_id}/events` with endpoint-, Entity-, and exclusive-position-scoped unsigned base64url keyset cursors; it defaults to 50 items, accepts 1–200, omits totals, and omits the final page's cursor. It returns accepted and rejected records without filters and exposes only the schema-constrained reported name, disposition, rejection code, and diagnostic timestamps, never Adapter, runtime, or correlation IDs, the fingerprint, receive order, or raw envelopes. Rejections for unknown Entity IDs have no browse route. SQLite retains entity events for a fixed internal 30 days from Core record time, pruned by the shared startup and hourly maintenance worker in batches of 500 with one cutoff per sweep and no separate timer or Core setting; the row provides duplicate protection only while retained.
- Core publishes **Device Facts** on `hearth.v1.core.fact.entity.<entity_id>.<family>.<variant>` for accepted Observations and accepted Entity Events; `<family>` is `observation` or `entity-event` with the fixed variant sets, and each fact is a strict v1 `*-fact` schema under `contracts/v1` carrying a stable `fct_<UUIDv7>` envelope `id` that is also published as `Nats-Msg-Id`, while the durable `obs_`/`evt_` source ID stays `causation_id`. The devices transaction that establishes the evidence writes the pending fact row in the same commit, and one relay publishes pending facts oldest-first into the bounded JetStream stream `HEARTH_DEVICE_FACTS_V1` (`LimitsPolicy`/`FileStorage`, subject filter `hearth.v1.core.fact.>`, seven days, one GiB, `DiscardOld`, unlimited message size, a two-hour duplicate window and no subject transform), deleting each row only after a broker `PubAck` naming that stream. Publication is therefore at-least-once from the outbox with broker deduplication bounded by the duplicate window, so a consumer may see a duplicate and must stay idempotent on the fact identity; `emitted_at` is Core's commit time stored at enqueue and reused by every retry, and the persisted inbound `traceparent`/`tracestate` are restored on republication. The Device Fact publishing foundation provisions the stream and no reader consumer, while the Automations module provisions its own consumer; no HTTP fact endpoint exists; the durable SQLite record and HTTP read APIs remain authoritative. Command lifecycle is not a fact family: no Command schema, subject, outbox row or sink exists, and Command status transitions, including startup interruption, remain authoritative only in the SQLite `commands` table and the HTTP Command read APIs.
- Only an accepted first-seen Observation (`applied` or `unchanged`) or an accepted first-seen Entity Event queues a fact. Rejected, duplicate and identity-conflict input queues nothing; the fact row and its evidence commit in one devices transaction, so an outbox identity-mint or insert failure rolls the evidence back for inbound redelivery, while a later publication failure never changes the committed source. The single relay publishes pending rows in durable enqueue order and deletes only what the broker acknowledged; a transient outbox, publish, acknowledgement or delete failure keeps the row and retries with the same identity and bytes, and a deterministic corrupt or unmappable row keeps the row, logs `device_fact.poison` and fails readiness. A Command status transition queues no fact at all, while an accepted Observation that satisfies a Command still queues its own Observation fact. Observations are not Command lifecycle substitutes: a stateless `dispatched` or a failure outcome produces no accepted Observation. Fact IDs are identities, not sequence numbers, and there is no global order across families, Entities or Core restarts.
- One shared Core NATS connection carries subscriptions, request/reply, JetStream ingestion and fact publication; there is no dedicated fact connection, no connection epoch or freshness fence, no volatile dispatcher queue and no reconnect-buffer distinction. The shared connection's socket writes stay bounded to one second so a synchronous shutdown close cannot wait on the client's one-minute default, and fact publication uses the same JetStream context as ingestion. Every reader owns its recovery policy: a named durable consumer resumes from its own acknowledgement floor, a new `DeliverNew` consumer tails only future facts, and The Device Fact publishing foundation creates no reader consumer; the Automations module creates one named durable consumer with the recovery policy stated below. Retention is bounded to seven days or one GiB with oldest-first eviction, so a reader that falls further behind than that permanently misses evicted facts.
- Publication is at-least-once from the outbox with broker deduplication bounded by the stream's two-hour duplicate window: a retry whose `PubAck` or row delete was lost is collapsed inside the window and stored again after it, so consumers stay idempotent on the fact identity and never assume one stored message per durable fact. Device Fact contracts are externally supported but carry no security guarantee: anyone with broker access may read canonical State values, forge a fact, or publish into or purge `HEARTH_DEVICE_FACTS_V1`, facts are unsigned, and the expected future policy reserves `hearth.v1.core.fact.>` publish and the fact stream for Core and denies the namespace to Adapters and subscribers.
- Fact-driven Automations form a separate product module that owns durable runtime-managed definitions, typed single-Fact matching, atomic Run-or-Skip admission, immutable Run snapshots, ordered static Command Steps, execution history, and retention while `devices` continues to own Entities, facts, and Commands. The `automations` domain consumes its existing definition and runtime repository interfaces; `internal/modules/automations/sqlite` implements them with one repository and owns its query sources and generated `dbsqlc` package. SQLite depends on the domain, never the reverse, and application assembly injects the concrete repository. Fact admission evaluates current definitions and commits matching receipts, Runs, Skips, and initial Steps in one transaction; pure domain policies operate on transaction-loaded values, and Run workers start only after commit. One named durable consumer reads both Device Fact families, starts at the stream tail only on first creation, resumes its acknowledgement floor thereafter, and records per-Automation `stale_fact` skips instead of executing a matching fact more than 30 seconds after Core's `emitted_at`; `(fact_id, automation_id)` makes matched outcomes idempotent. An Automation permits 1–32 alternative Triggers and 1–32 sequential Steps, has at most one active Run, allows explicit manual invocation even while disabled, and deliberately has no process-wide Run cap, execution retry, crash replay, multi-Fact condition, or history scan; `specs/automations.md` owns the complete implementation contract.
- Core shutdown joins Command workers, drains or stops the Entity Event consumer before the Observation consumer while the Device Fact relay still publishes, then drains `devicesnats.DeviceFactRelay` within its five-second deadline, and only then drains transports, the shared NATS connection and SQLite. Rows still pending when that deadline expires stay in the durable outbox for the next Core process, which re-reads the oldest pending fact first; the relay's retry reuses each row's stable identity and bytes, so a duplicate is possible only after the stream's duplicate window has elapsed. Already dispatched reports still commit; unprocessed or unacknowledged reports remain in the stream for the next Core process; device ingestion never replays its own Event history into Commands, while the separate Automation fact consumer may admit a fresh retained Fact; no ingestion callback waits for a Command. Durable Observation and Entity Event callbacks run under a lifecycle context detached from process cancellation and from the dependency context shared by command workers, health, and hourly maintenance, so dependency cancellation during shutdown cannot abort a report or projection that already entered SQLite; that consumer context is canceled only after both consumers have drained or stopped, on normal and error exits alike. The Core-offline guarantee covers broker-acknowledged input only while NATS and JetStream remain available and the Adapter process lives, within stream limits: initial claim and registration need Core, unacknowledged work is not protected against Adapter process death, NATS process loss is not covered, and stream limits can discard old input during a long Core outage. Transient heartbeat failures retry in the Session lifecycle context with no fixed missed-tick cutoff, while a permanent or fenced outcome or explicit close still terminates the Session. Entity Event ingestion has no history-scan replay path and no direct automation callback; accepted facts may drive the separate Automations module, while physical-device mapping remains Adapter-owned.
- HTTP pagination cursors are unsigned, versioned base64url JSON positions scoped to their endpoint, optional Device or disposition filter, parent Device, and parent Entity. They provide position rather than authority and are not security credentials.
- `POST /v1/entities/{entity_id}/commands` accepts `{"operation":"set","parameters":{"value":true}}` for the first power Entity and waits synchronously for terminal outcome (satisfaction or dispatch) or deadline failure.
- HTTP errors use Huma's standard RFC 9457 Problem Details model and validation conventions. Command status mappings include unhealthy or unrouted Adapter 503, Entity-unavailable rejection 503, upstream rejection 502, outcome timeout 504, and internal failure 500.
- The unauthenticated HTTP API binds to its configured address. Configuration examples remain loopback-only; non-loopback binding is an explicit operator choice for trusted networks, and untrusted network exposure requires authentication and a deployment decision.
- Each first-slice process owns a separate YAML file for non-secret configuration; the Home Assistant adapter reads its token from a separate local secret file.
- Adapter health is one `unknown`, `healthy`, or `unhealthy` assessment derived from runtime evidence and the active runtime's configured-external-system report. The report remains heartbeat input rather than a separate persisted or exposed health model. Current health records whether Core or the Adapter supplied the effective evidence and retains Adapter source time only for Adapter-supplied evidence. Core request/reply heartbeats immediately repeat the Adapter's current assessment, renew only the dedicated runtime lease, and commit status or reason-code transitions; unchanged reports refresh current evidence without creating history. Graceful release makes health immediately `unhealthy`.
- Entity availability is `unknown`, `available`, or `unavailable`; Devices have no health. Only explicit acknowledged reports from the active healthy owning Adapter set Entity availability, reports may still update disabled Entities, and an unhealthy Adapter makes every owned Entity effectively unavailable. A transition away from healthy deletes current Entity reports transactionally, so later recovery requires fresh atomic partial batches of 1-256 owned Entities; unknown is Core-derived and unavailable reports require a reason.
- An unhealthy owning Adapter causes a new Command to fail as `adapter_unhealthy` before dispatch. Unknown Adapter health is attempted only when an active runtime route exists; an unavailable Entity with a healthy owner is also attempted, and a fresh typed rejection may fail as `entity_unavailable` without itself writing availability. Entity disablement still wins when both conditions apply.
- Health and availability use Core receive order and Core-owned time for canonical transitions while retaining Adapter-observed source time for diagnosis. Negative reports require stable reason codes: shared codes use the `hearth.` namespace and Adapter-defined codes use `adapter.` without coupling validation to runtime software metadata. Status or reason-code changes create history transitions; repeated evidence does not.
- At startup and reconnect, the disposable Home Assistant adapter establishes its state-change subscription before requesting a current snapshot, buffers events during snapshot acquisition, and reconciles them by Home Assistant `last_updated` before live publication so no transition is lost or allowed to overwrite a newer snapshot. It correlates concurrent WebSocket requests by request ID and uses each successful `Accept` result to publish that Command's linked refresh.
- A command is dispatched even when canonical state already matches its requested target.
- After upstream acceptance, the adapter actively refreshes state and publishes a fresh observation linked to the command ID, including when no state-change event occurred.
- An observed command outcome is satisfied only after the linked post-dispatch canonical Observation satisfies the registered operation's catalog outcome policy; for the first `set` operation this means its value matches the requested value. A dispatched operation instead terminates as `dispatched` on durable acceptance with no observation. This claims that the outcome was observed, not that the Command caused it.
- Version 1 Adapter routes atomically cut over from stable-slug-only subjects to a stable-slug session claim plus runtime-scoped Registration, heartbeat, release, Observation, Command, Entity enablement, and Entity availability subjects. The claim carries the SDK-generated runtime ID; later payloads do not repeat it. Entity availability uses acknowledged Core NATS request/reply with Adapter retry for transient failures; Core receipts make accepted request IDs idempotent across health changes, and a batch rejects atomically on any invalid or wrongly owned entry. Core, embedded contracts, first-party Adapters, the Go SDK, and NATS resources ship this incompatible cutover together, and mixed versions remain unsupported.
- Echo v5 and Huma v2 provide HTTP transport; application assembly constructs them and owns process-global HTTP framework policy, while the `devices` module owns operation registration and transport mapping. OpenAPI is exposed at runtime and is not committed as a generated artifact.
- Local development runs Go binaries natively through mise and starts NATS plus Mosquitto through the local Compose stack. Release image packaging exists for each executable, while production supervision and deployment topology remain deferred.
- The core exposes `/healthz` and `/readyz` on its configured HTTP address; readiness requires migrated SQLite, the shared NATS connection connected, the validated Device Fact stream, an active Device Fact relay, provisioned Observation, Entity Event, and Automation JetStream resources with compatible configuration, active Observation, Entity Event, and Automation consumers, and open Automation and Command admission; it never requires an external fact subscriber, a fact consumer Core does not own, a nonempty outbox or proof that a publication was received, and it never waits for unread Entity Event backlog or gates ingestion. Core readiness supersedes Adapter health for diagnosis: readiness failure pauses the supervisor's lease expiry without changing persisted Adapter or Entity reads, and recovery grants one lease interval of expiry grace before polling resumes. Other Adapter operations verify active runtime identity but do not expire leases. Persisted child assessments remain visible but non-authoritative while `/readyz` fails. Adapters retry transient claim and registration failures until the core is available and stop on schema-defined permanent rejection.
- [ADR 0022](adr/0022-evaluate-conditions-from-state-snapshots.md) defines optional Automation Conditions over coherent current Entity State evidence. Devices owns the batch State read outside automation transactions; final admission uses current transaction-loaded definitions, requires complete evidence coverage before writes, and commits matched-Fact outcomes and receipts atomically. Conditions evaluate once with three-valued logic; false/unknown Conditions produce explainable automatic or manual Skips, and manual invocation permits an explicit recorded bypass; [the Conditions spec](../specs/automation-conditions.md) owns the implementation contract.
