# Architecture

**Status:** Evolving; only constraints backed by accepted decisions are stated here.

## Accepted constraints

- The product and user-facing namespace are **Hearth**. `hearthd` names only the core daemon executable; the planned management CLI is `hearth`; companion processes use `hearth-` names; and wire, Entity-type, schema, and Go module identifiers use the `hearth` namespace.
- One trusted Hearth deployment owns one household; version 1 has no separate Site or Home object.
- Home Assistant remains optional rather than mandatory: a Household may eliminate it for a functional replacement or retain it indefinitely as an external system of record for selected objects.
- Home Assistant connectivity runs in a permanently supported inbound Bridge process separate from the core and communicates across versioned NATS contracts. Home Assistant owns bridged objects' external configuration and lifecycle; Hearth owns their canonical Device and Entity identities.
- Core models and wire contracts contain no Home Assistant identifiers, service-call vocabulary, payloads, or lifecycle assumptions.
- The core, simulator, and first-party adapters use module path `github.com/mholtzscher/hearth`. The fixed implementation stack is Go, official `nats.go`, Echo v5, Huma v2, `modernc.org/sqlite`, Goose, sqlc, `coder/websocket`, `jsonschema/v6`, YAML v3, Google UUID, and OpenTelemetry propagation; wire contracts remain language-neutral.
- A thin Go adapter SDK exposes generic Session methods for Adapter-instance registration and presence, complete Inventory reconciliation, current status reporting, durable Observation publication, and ephemeral Command serving. Schema-backed typed routing and the built-in power/v1 and brightness/v1 facades let Go adapters describe Entities, handle Commands, and encode Observations without raw JSON or operation-name switches. `PublishObservation` retries one generated envelope through transient disconnects and returns only after JetStream acknowledges persistence or the call context expires. Current status is coalesced only in memory and retried until acknowledged; the SDK has no durable outbox. Command handler invocations may overlap, including for one Entity; adapters must be concurrency-safe and may serialize internally only when their vendor protocol requires it.
- The SDK propagates explicit message, correlation, causation, and command IDs in JSON and W3C trace context in NATS headers.
- One cohesive `devices` product module owns Adapter lifecycle as it affects Device ownership, Inventory reconciliation, State projection, and Command behavior; those concerns split only after distinct rules and change pressure justify new seams. Its `internal/modules/devices/nats` transport owns core-side device NATS payload DTOs, wire/domain mapping, instance/heartbeat/Inventory/status serving, Observation consumption and JetStream policy, and Command sending. Shared Hearth v1 envelope, schema codec, subject, route, and W3C trace mechanics live in `internal/contracts/v1/natswire`; it defines no device payload DTOs. Application assembly retains NATS connection creation, validator compilation, readiness, and process lifecycle.
- Device NATS transport lifecycle names describe the messaging interaction: a `Server` handles Core NATS request/reply and publishes correlated responses, while a `Consumer` reads from a durable JetStream consumer and owns acknowledgement and redelivery behavior. Instance, heartbeat, Inventory, and current-status interactions use Servers; Observation uses `ObservationConsumer`.
- Devices group independently addressable entities; state reads and commands target entities.
- Hearth assigns immutable canonical IDs to devices and entities; adapter-specific external IDs are mappings and ownership can change without changing canonical identity. Canonical and message IDs are UUIDv7 values with type prefixes such as `dev_`, `ent_`, `obs_`, and `cmd_`.
- Adapters submit a complete explicit Inventory of configured external objects. Each Binding may describe multiple typed Entities, and the core returns canonical IDs only after transactionally applying valid descriptors, external mappings, lifecycle changes, and current issues. Operation-key presence means support. Names and support may change without changing canonical identity; Entity type is immutable for one Entity key. Language-neutral JSON Schemas are authoritative for support, State, and parameters; a versioned language-neutral Entity-type manifest defines deadlines, outcome matching, and cross-document validation. Build-time generation derives typed Go, SDK facades, conformance tests, and core catalog assembly. Runtime type loading, general discovery/approval, feature negotiation, configuration schemas, and checkpoints remain deferred.
- Each Adapter instance has a configured subject-safe slug. Each configured external object has a persisted configured selector plus stable Adapter-scoped Binding key so canonical IDs survive external-ID changes; ambiguous identity conflicts require explicit reconciliation.
- Milestones must provide household value and meaningful NATS learning.
- A production use of NATS must solve a concrete durability, isolation, routing, or observability problem.
- Version 1 wire contracts use a compact Hearth envelope and versioned JSON checked against language-neutral JSON Schemas. Its exact top-level fields are `id`, `schema`, `emitted_at`, required `correlation_id`, optional `causation_id`, and `data`. Canonical schema JSON and a tiny `embed.FS` wrapper live together in importable `contracts/v1`; the core and SDK validate the same embedded schemas at runtime. Incompatible major versions appear in both the subject prefix and each stored payload's schema identifier.
- Wire timestamps are UTC RFC3339Nano strings; malformed or non-UTC values are rejected at the contract edge.
- The SDK generates adapter publication IDs and envelope metadata while adapters supply domain data and diagnostic source times.
- Adapter observations are retained in a file-backed JetStream Limits stream for seven days or one GiB, whichever is reached first, discarding oldest messages. The core uses one explicit-ack durable consumer with a 30-second acknowledgement wait, one maximum pending acknowledgement, and unlimited redelivery. Processed observation IDs remain in SQLite for at least eight days so any retained redelivery stays idempotent; the receipt backing current State remains until a newer Observation supersedes it.
- Each Observation records core-owned `observed_at` from its JetStream server timestamp, adapter-supplied `adapter_received_at`, optional upstream `source_updated_at`, and an internal SQLite `receive_order`. Canonical State follows the tie-free logical `receive_order`; timestamps are operator/history metadata. An `adapter_received_at` more than one minute ahead of `observed_at` is accepted and logged as clock skew.
- Each first-seen, valid, correctly owned Observation advances canonical State. An incoming value must satisfy current support; equality schema-decodes the persisted value without reinterpreting it under support that may have narrowed since persistence. An Observation whose value the Entity-type catalog considers equivalent advances its ID/timestamps and is `unchanged`; a value the catalog considers different is `applied`.
- The core owns Adapter status, Inventory and lifecycle, canonical State, external-ID mappings, Observation receipts, and Command history transactionally in SQLite; NATS KV is not used for these models.
- SQLite migrations use Goose and query code is generated in one platform database package with module-organized query sources; generated persistence types do not cross the `devices` module seam.
- Every observation has an immutable ID that the core records transactionally with its disposition and state projection, making exact JetStream redelivery a no-op.
- Permanently invalid Observations are diagnosed in structured logs with safe payload metadata and acknowledged; raw input remains in the seven-day stream. Transient infrastructure failures remain unacknowledged for redelivery. Valid applied, unchanged, duplicate, and rejected Observations are acknowledged only after the SQLite transaction commits.
- Immediate commands use adapter-scoped Core NATS request/reply, take their end-to-end deadline from the registered operation definition, and are not queued for later adapter recovery. The first `hearth.power/v1` `set` operation has a fixed ten-second deadline.
- Commands for one Entity may overlap; the core does not guard, queue, or supersede them. Each Command has an independent ID, durable record, in-memory waiter, and operation-defined deadline, and only its own linked Observation satisfying the catalog outcome policy can complete it. Interleaved Commands may both be satisfied at different receive orders or may cause one another to time out; canonical State still follows core receive order.
- Command delivery and outcome waits are ephemeral and in memory, while SQLite stores a minimal non-replayable record of each attempt and terminal outcome for diagnosis and future history. The record commits as `requested` before dispatch; a linked Observation satisfying the catalog outcome policy marks only that Command `satisfied` in the same transaction as State projection. After the `requested` record commits, the core proceeds with dispatch and retains that lifecycle until linked outcome or the operation-defined deadline even if the HTTP client disconnects. Only the startup-wide interruption path may mark persisted `requested` and `accepted` records `interrupted`; per-command completion cannot claim a core restart. A core restart loses active waits and never redispatches them.
- `GET /v1/entities/{entity_id}` returns Entity metadata, lifecycle, effective availability, and current State; an active available Entity that has never been observed returns `state: null` rather than 404 or synthetic State.
- `POST /v1/entities/{entity_id}/commands` validates the type-specific Operation and waits synchronously for outcome satisfaction or deadline failure. Active unavailable attempts are recorded without dispatch; retired Entities reject the request without creating a Command.
- Command failures use stable JSON error codes and status mappings: missing Adapter or unavailable Entity 503, retired Entity 409, upstream rejection 502, outcome timeout 504, and internal failure 500.
- During native development the unauthenticated HTTP API binds only to loopback; network exposure requires a later authentication and deployment decision.
- Each process owns a separate YAML file for non-secret configuration; the Home Assistant Bridge reads its token from a separate local secret file and selects registry-backed lights through an explicit entity-ID allowlist.
- Adapter presence, upstream status, Entity availability, and retirement are generic Hearth concepts. Unavailability retains last State and blocks new Command dispatch; a ten-second SDK heartbeat gives Adapter presence a 30-second lease.
- At startup and reconnect, the Home Assistant Adapter establishes its state-change subscription before requesting a current snapshot, buffers events during snapshot acquisition, and reconciles them by Home Assistant `last_updated` before live publication so no transition is lost or allowed to overwrite a newer snapshot. It correlates concurrent WebSocket requests by request ID and explicitly publishes each accepted Command's own linked refresh.
- A command is dispatched even when canonical state already matches its requested target.
- After upstream acceptance, the adapter actively refreshes state and publishes a fresh observation linked to the command ID, including when no state-change event occurred.
- A command outcome is satisfied only after the linked post-dispatch canonical Observation satisfies the registered operation's catalog outcome policy; for the first `set` operation this means its value matches the requested value. This claims that the outcome was observed, not that the Command caused it.
- Adapter NATS subjects are Adapter-scoped. Core request/reply uses `hearth.v1.adapter.<adapter>.instance`, `.heartbeat`, `.inventory`, and `.status`; Observations use `.observation.<entity>` and Commands use `.command.<entity>.<operation>`.

- Echo v5 and Huma v2 provide HTTP transport; application assembly constructs them and owns process-global HTTP framework policy, while the `devices` module owns operation registration and transport mapping. OpenAPI is exposed at runtime and is not committed as a generated artifact.
- Local development runs Go binaries and NATS natively through devenv; container packaging is deferred until deployment work.
- The core exposes loopback `/healthz` and `/readyz`; readiness requires migrated SQLite, NATS connectivity, provisioned JetStream resources, and an active observation consumer. Adapters retry transient instance/Inventory failures until the core is available and stop on schema-defined permanent identity or descriptor rejection.

## Undecided

Message and HTTP contracts beyond the approved first-light and Home Assistant Bridge specifications, production deployment topology beyond released host binaries, automation semantics, frontend architecture, native Adapter scope, and all later roadmap technology choices remain proposals until reviewed.
