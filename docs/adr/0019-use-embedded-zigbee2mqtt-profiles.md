# Use embedded Zigbee2MQTT profiles for entity mapping

Zigbee2MQTT entity mapping moves from handwritten Go planners into repository-owned embedded JSON profiles validated by the authoritative JSON Schema `urn:hearth:schema:zigbee2mqtt-profile:v1` and compiled into one immutable `ProfileCatalog` before any NATS or MQTT connection. Profiles declare mapping intent; a closed set of twelve Go strategies keeps all typed state, command, and outcome behavior. Version 1 loads only embedded profiles at startup and defers solely user-supplied and runtime-loaded profile manifests.

Each embedded file holds one version-1 document, either a `planner-profile` with an explicit unique `order` or a `profile-override` with an exact vendor, model, and optional firmware-build selector. Filenames fix diagnostic order only and never planning precedence. Profiles evaluate in ascending order: `light` at 10 as primary for device kind `light`, `relay` at 20 as primary for `relay`, `ambient-sensors` at 30 and `linkquality` at 40 as supplementals for `sensor`. Those are the only valid contribution kind/role combinations in version 1: `light` and `relay` are primary, while `sensor` is supplemental. The existing merge rule is unchanged: the first non-empty primary contribution wins, later primaries are discarded, every supplemental contribution appends in order, and the first non-empty supplemental establishes device kind when no primary survives.

Candidate groups select roots through exact expose type and optional exact name matches. By default they evaluate every match in retained inventory order; a root selector with `"cardinality":"unique"` instead uses device-wide exact-one selection and evaluates nothing when the match is missing or duplicated. This explicit cardinality preserves mappings such as link quality whose existing contract treats duplicate device roots as ambiguous without adding a mapping-specific Go branch. Each entity rule selects evidence through a closed source union: `root` passes the selected root expose, `feature` performs the exact-one `UniqueFeature(type, name)` lookup inside that root, and `derived` accepts only `color-mode` and plans from declared `requires_any` sibling plans. A present `gate_rule` must be the first entity rule and gates its siblings. Candidate groups deduplicate on the gate's scoped key by dropping every candidate that shares a duplicate gate key, including each candidate's siblings; unique candidates retain inventory order. Device entities use the existing `UniqueRoot(type, name)` behavior exactly once after candidate groups and evaluate only when their `requires_group_survivor` group retains a candidate. Entity `identity.key` is always the unscoped stable base key; Go applies scoped identity and external IDs, so profiles cannot change observable identity.

The twelve strategies are `binary-power`, `brightness`, `color-temperature`, `color-xy`, `color-hs`, `color-mode`, `startup-color-temperature`, `temperature`, and `enum-setting`, each accepting exactly `{}`; `numeric-sensor` with required accepted upstream units, output unit, integer or float format, and a fixed or upstream-or-fallback bound union; `numeric-setting` with required accepted units and an optional unit; and `enum-action` with exactly `set-only` or `includes-set` access. `binary-power`, `brightness`, `color-temperature`, `color-xy`, `color-hs`, and `startup-color-temperature` accept only feature sources; `color-mode` accepts only the derived source; `temperature`, `numeric-sensor`, `numeric-setting`, `enum-setting`, and `enum-action` accept only root sources. Any other strategy/source pairing is a startup-fatal `strategy_source_mismatch`. Strategy parameters compile once at catalog load and strategies receive typed values, never unvalidated JSON.

Overrides address proven vendor, model, and firmware quirks without making the generic catalog model-specific. For one target rule the base layer is overlaid by at most one matching general vendor/model patch and then at most one matching exact-build patch; each present field replaces that complete field, `enabled` defaults to true, and an exact-build patch may re-enable a generally disabled rule. Two general patches for the same vendor, model, and target conflict, exact-build selectors for the same vendor, model, and target must hold disjoint build-ID sets, and candidate-entity patches take `source` while device-entity patches take `expose`, with the wrong field rejected as `override_target_kind_mismatch`. Patches may disable a rule, replace its source or expose match, or fully replace strategy parameters against the target strategy; they cannot add rules, change rule IDs, entity keys, display names, strategy names, contribution, group, dependency, or order, and selector strings never enter binding or entity identities.

Whole-catalog compilation fails startup on any schema, limit, reference, strategy, or override conflict and never returns a partial catalog, while malformed runtime inventory stays isolated per device and expose. This split keeps repository defects fail-fast and one malformed device from suppressing valid inventory. Handwritten planners remain only as temporary differential-test oracles until parity cutover deletes them, and observable binding keys, device kinds, entity keys, external IDs, names, types, support, order, routes, rejection codes, state conversion, command payloads, refresh, and outcome policy stay byte-identical.
