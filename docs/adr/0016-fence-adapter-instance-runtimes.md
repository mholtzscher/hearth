# Fence each Adapter instance to one active runtime

Each Adapter instance permits one active runtime. A Core session claim issues a runtime ID that scopes every post-claim Adapter-originated NATS subject and every Command subject until graceful release or supervisor-owned lease expiry. Payloads do not repeat the runtime ID; the NATS subject is the authoritative wire source. Core parses the route and transactionally rejects writes from stale runtime IDs, and the SDK terminates a fenced session. The SDK subscribes only to its runtime's Command subject, so a replacement runtime does not receive Commands committed for an earlier runtime.

This prevents duplicate Command delivery and stale publications while preserving the stable Adapter slug across restarts. A captured JSON payload does not identify its runtime without the accompanying NATS subject, so transport diagnostics and retained-message handling must preserve the subject. The runtime ID is a fencing mechanism rather than Adapter identity or authentication because Hearth runs one trusted household and does not yet need replicated Adapters or dynamic NATS credentials. The incompatible subject changes ship as one atomic version 1 Core, contract, SDK, first-party Adapter, and NATS resource cutover.
